# RTOS 任务调度与实时性嵌入式面试分享题库

> 适用场景：嵌入式软件、MCU 驱动、FreeRTOS、工业控制、电机控制、数字电源、通信网关和多任务系统方向面试。
>
> 说明：RTOS 面试不只是会创建任务。面试官通常会继续追问任务状态、抢占调度、时间片、中断通信、优先级反转、栈溢出、动态内存、死锁、调度延迟和硬实时任务怎样落地。

## 1. 分享主线

建议从“一个任务为什么没有运行”切入：

```text
任务当前处于运行、就绪、阻塞还是挂起状态？
    ↓
调度器怎样根据优先级、抢占和时间片选择任务？
    ↓
周期任务怎样避免累计漂移？
    ↓
中断怎样用队列、信号量或任务通知唤醒任务？
    ↓
为什么中断必须调用 FromISR 接口？
    ↓
多个任务访问同一资源时，互斥锁解决了什么问题？
    ↓
优先级反转、死锁、栈溢出和内存碎片怎样定位？
    ↓
控制中断、通信任务、日志任务和看门狗怎样分工？
```

这条线先把调度条件讲清楚，再进入任务间通信和资源保护，最后落到实时性、可靠性与系统架构。

### 2.4 第一等级：基础知识详细答案

#### 2.4.1 RTOS 和裸机前后台系统有什么区别？

裸机前后台系统常见结构是：中断负责响应事件，主循环按固定顺序轮询各模块。它简单、开销小，但业务增多后容易出现某个模块阻塞整个主循环、响应时间难以估计的问题。

RTOS 提供任务、优先级、阻塞等待、超时和任务间通信。任务等待事件时可以主动阻塞，把 CPU 交给其他就绪任务。

面试回答：

> RTOS 用调度器管理任务的就绪和阻塞，让不同实时性要求的功能按优先级运行。“同时跑多个函数”只是表面结果，系统也因此引入了栈、调度、同步和资源竞争问题。

#### 2.4.2 FreeRTOS 任务有哪些状态？

| 状态 | 含义 | 常见进入方式 |
| --- | --- | --- |
| Running | 当前占用 CPU | 被调度器选中 |
| Ready | 已满足运行条件，等待 CPU | 创建完成、事件到来、超时 |
| Blocked | 等待事件或时间 | 等队列、信号量、通知、delay |
| Suspended | 不参与正常调度 | `vTaskSuspend` |

单核 MCU 同一时刻通常只有一个任务处于 Running。高优先级任务只有进入 Ready，才有资格抢占当前任务。

#### 2.4.3 阻塞态和挂起态有什么区别？

阻塞态通常带有等待条件：

- 队列收到数据。
- 信号量可用。
- 任务通知到达。
- 等待时间超时。

条件满足后，内核会把任务移回 Ready。挂起态不依赖这些正常等待条件，通常需要 `vTaskResume` 或对应的 ISR 恢复接口显式恢复。

周期任务应该使用 delay 或事件等待进入 Blocked，不应依靠 suspend/resume 模拟普通周期调度。

#### 2.4.4 抢占调度和时间片分别解决什么问题？

抢占处理不同优先级：高优先级任务一旦就绪，可以抢占正在运行的低优先级任务。

时间片处理同优先级：多个相同优先级任务同时就绪时，可以在 Tick 到来后轮流运行。若关闭时间片，同优先级任务仍可能在阻塞、让出 CPU 或其他调度点发生切换。

需要注意，FreeRTOS 中任务优先级数值越大，任务优先级越高；Cortex-M 的 NVIC 中断优先级数值通常相反，不能混用这两套规则。

#### 2.4.5 `vTaskDelay` 和 `vTaskDelayUntil` 有什么区别？

`vTaskDelay(N)` 从“当前调用时刻”开始等待 N 个 Tick。如果任务每次执行时间不同，周期会随执行时间累积漂移。

`vTaskDelayUntil` 以预期唤醒时刻为基准，适合固定周期任务：

```c
TickType_t lastWake = xTaskGetTickCount();

for (;;) {
    RunPeriodicWork();
    vTaskDelayUntil(&lastWake, pdMS_TO_TICKS(10));
}
```

如果任务本次执行已经超过整个周期，`vTaskDelayUntil` 不能消除超时，只能让软件更容易发现周期预算被突破。

#### 2.4.6 上下文切换的开销来自哪里？

任务切换时，内核和移植层需要保存当前任务寄存器、栈指针及必要的浮点上下文，选择下一个 Ready 任务，再恢复它的上下文。

开销受以下因素影响：

- CPU 架构和寄存器数量。
- 是否使用 FPU。
- 中断嵌套和调度路径。
- Cache、MPU 和内存速度。
- 切换频率。

切换时间通常很短，但把大量小任务设置成极高频率，仍会增加 CPU 占用和抖动。

### 2.5 第二等级：驱动应用详细答案

#### 2.5.1 队列、信号量和任务通知怎么选？

| 机制 | 主要用途 | 特点 |
| --- | --- | --- |
| Queue | 在任务之间传递固定大小的数据项 | 默认复制数据，可多生产者、多消费者 |
| Binary Semaphore | 表示事件发生或资源可用 | 不携带业务数据 |
| Counting Semaphore | 统计事件次数或可用资源数量 | 有最大计数值 |
| Mutex | 保护共享资源 | 有所有者，支持优先级继承 |
| Task Notification | 通知一个固定任务 | 开销小，可表示计数、位或数值 |
| Event Group | 等待多个状态位组合 | 适合 AND/OR 条件同步 |

面试回答：

> 需要传数据就用队列；只通知一个固定任务可以优先考虑任务通知；需要累计事件次数可以用计数信号量；共享总线和不可重入资源用互斥锁。选择依据是数据语义、接收者数量和实时性要求。

#### 2.5.2 为什么中断里必须使用 FromISR 接口？

普通队列、信号量接口按照任务上下文设计，可能根据等待时间把当前任务加入阻塞列表，还会使用任务上下文对应的临界区和调度处理。

中断上下文不能阻塞等待，也不能直接调用任务级的切换流程。即使普通接口的等待时间传 0，也不代表整个内部实现变成 ISR-safe。

FromISR 接口有三个特点：

- 不在 ISR 中阻塞。
- 使用移植层提供的中断安全临界区处理。
- 通过 `pxHigherPriorityTaskWoken` 告诉调用者是否需要在 ISR 退出前请求调度。

典型写法：

```c
BaseType_t higherPriorityTaskWoken = pdFALSE;

xQueueSendFromISR(queue, &item, &higherPriorityTaskWoken);
portYIELD_FROM_ISR(higherPriorityTaskWoken);
```

#### 2.5.3 哪些中断可以调用 FreeRTOS API？

以 Cortex-M 端口为例，只有满足 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 限制的中断，才能调用 FreeRTOS 的 FromISR API。逻辑优先级特别高、用于极低延迟响应的中断不能调用内核 API。

常见错误来自 NVIC 优先级数值方向：数值越小，逻辑中断优先级通常越高。项目中还要结合 `configPRIO_BITS`、优先级分组和厂商 HAL 的参数定义核对。

面试回答：

> FromISR 不等于任何中断都能调用。优先级高于 FreeRTOS 可管理范围的中断必须完全独立于内核，只保存硬件状态或写入无锁缓冲，不能操作队列和信号量。

#### 2.5.4 互斥锁和二值信号量有什么区别？

二值信号量更适合事件同步，可以由一个任务或 ISR give，再由另一个任务 take。它没有严格的所有者语义。

互斥锁用于保护共享资源：谁获得锁，原则上由谁释放，并且带有优先级继承。ISR 不能获取互斥锁，因为 ISR 不能阻塞，也不存在正常的任务所有者关系。

SPI、I2C、文件系统和不可重入库函数通常使用互斥锁；“DMA 完成了”这类事件通常使用信号量或任务通知。

#### 2.5.5 临界区、挂起调度器和互斥锁怎么选？

| 手段 | 阻止什么 | 适合场景 |
| --- | --- | --- |
| Critical Section | 按端口规则屏蔽一部分或全部可管理中断 | 极短的任务/ISR 共享数据更新 |
| `vTaskSuspendAll` | 阻止任务切换，不阻止硬件中断 | 一小段不能被其他任务打断的操作 |
| Mutex | 阻止其他任务访问同一资源 | 可能持续较长的总线或模块事务 |

临界区必须很短，里面不能 delay 或等待队列。挂起调度器时中断仍然可能修改共享数据。互斥锁保护不了 ISR 和任务之间的并发访问，需要重新设计数据所有权或使用短临界区。

#### 2.5.6 软件定时器回调要注意什么？

FreeRTOS 软件定时器回调通常由同一个 Timer Service Task 串行执行。某个回调耗时过长，会拖延其他软件定时器命令和回调。

回调中应该：

- 做少量状态更新。
- 发送任务通知或队列消息。
- 避免长时间计算。
- 避免无期限阻塞。

硬实时 PWM、ADC 采样和快速保护不适合依赖软件定时器。

### 2.6 第三等级：项目实战详细答案

#### 2.6.1 优先级反转是怎么发生的？

典型过程有三个任务：

```text
低优先级任务 L 获得互斥锁
    ↓
高优先级任务 H 申请同一把锁，被阻塞
    ↓
中优先级任务 M 抢占 L
    ↓
L 无法运行，也无法释放锁
    ↓
H 的等待时间被 M 继续拉长
```

优先级继承会临时提高持锁任务 L 的优先级，让它尽快完成临界区并释放锁。释放后，L 恢复原优先级。

它不能修复过长临界区、锁内 delay、循环依赖或错误的锁顺序。工程上仍要缩短持锁时间，并避免在持锁期间调用可能阻塞的接口。

#### 2.6.2 死锁怎样产生，怎样预防？

常见死锁：任务 A 已持有锁 1，继续等待锁 2；任务 B 已持有锁 2，又等待锁 1。两个任务都无法继续。

预防方法：

- 规定全局统一的加锁顺序。
- 尽量减少嵌套锁。
- 获取锁设置合理超时，并记录失败现场。
- 不在持锁期间调用未知阻塞行为的模块。
- 把共享外设交给单一服务任务，其他任务通过队列提交请求。

定位时记录任务状态、当前持有的锁、等待对象和阻塞时长，比只看“某任务没运行”更有效。

#### 2.6.3 任务栈应该怎样评估？

任务栈需要容纳局部变量、函数调用链、保存的寄存器，以及可能的浮点上下文。大数组和递归会迅速增加栈需求。

常见手段：

- 开启 `configCHECK_FOR_STACK_OVERFLOW`。
- 实现 `vApplicationStackOverflowHook`。
- 使用 `uxTaskGetStackHighWaterMark` 检查历史最小剩余量。
- 在压力场景、异常分支和最大调用深度下测量。
- 将大缓冲区改为静态区、堆或专用内存池。

High-water mark 的单位通常是 `StackType_t`，不一定是字节，换算时要看端口定义。

#### 2.6.4 动态内存和静态内存怎么选？

动态创建方便按运行场景配置对象，但要考虑分配失败、碎片和运行期确定性。静态创建要求预先提供 TCB、栈和对象缓冲区，内存占用更容易审计。

FreeRTOS 常见 heap 实现关注点：

- `heap_1`：只分配不释放，简单确定。
- `heap_2`：可释放，但不合并相邻空闲块。
- `heap_4`：可释放并合并相邻空闲块，较常用。
- `heap_5`：支持多个不连续内存区域。

安全或长生命周期控制系统常在初始化阶段完成所有对象创建，运行期避免频繁 malloc/free。

#### 2.6.5 控制中断和 RTOS 任务怎样分工？

推荐按实时性分层：

```text
定时器 / ADC / 比较器中断：
    固定时刻采样
    运行短小的硬实时控制
    更新 PWM
    执行快速保护

高优先级任务：
    故障后处理
    控制模式切换
    参数同步

普通任务：
    通信、日志、UI、存储和诊断
```

ISR 要有明确的最坏执行时间。日志、动态内存、阻塞总线访问和复杂协议解析不应进入硬实时控制路径。

#### 2.6.6 RTOS 能自动保证硬实时吗？

不能。RTOS 提供可配置的优先级调度和同步机制，最终响应时间还取决于：

- 高优先级 ISR 的最长执行时间。
- 关中断和临界区时长。
- 任务最坏执行时间 WCET。
- 更高优先级任务的抢占。
- 锁竞争、DMA、Cache 和总线延迟。
- Tick 粒度及调度实现。

硬实时设计需要计算和测量最坏情况，不能只看平均运行时间或“平时没有超时”。

#### 2.6.7 看门狗任务怎样避免假喂狗？

单独创建一个高优先级任务定时喂狗并不可靠，因为其他业务任务可能已经卡死，而喂狗任务仍然正常运行。

更合理的方式：

1. 每个关键任务在完成一次有效工作后更新心跳或周期计数。
2. 监控任务检查所有关键心跳是否在时间窗口内更新。
3. 系统状态、调度延迟和关键外设也满足条件后，才喂硬件看门狗。
4. 复位前尽可能把故障码、任务状态和复位原因保存到保留区。

### 2.7 常见计算与场景模板

#### 2.7.1 Tick 与延时精度

如果 `configTICK_RATE_HZ = 1000`：

```text
1 Tick = 1 ms
pdMS_TO_TICKS(10) = 10 Ticks
```

任务被解除阻塞后只是进入 Ready，实际开始运行还要等待调度。因此 `vTaskDelay(10)` 表示至少阻塞相应 Tick 数，不等于严格在 10 ms 时刻执行。

#### 2.7.2 周期任务怎样避免累计漂移？

假设任务周期为 10 ms，任务本身每次执行约 2 ms：

```text
使用 vTaskDelay(10 ms)：
周期约为 2 ms + 10 ms = 12 ms，并受执行时间波动影响

使用 vTaskDelayUntil(..., 10 ms)：
唤醒基准按 10 ms 推进，正常情况下周期保持约 10 ms
```

#### 2.7.3 CPU 利用率怎样做初步估算？

对一组周期任务，可以先做粗略估算：

```text
U = Σ(Ci / Ti)

Ci：任务最坏执行时间
Ti：任务周期
```

例如三个任务分别为 `1/10 ms`、`2/20 ms`、`5/100 ms`：

```text
U = 1/10 + 2/20 + 5/100
  = 0.25
  = 25%
```

这只是初步负载估算，还没有计入 ISR、上下文切换、锁阻塞、DMA 竞争和非周期任务，也不能单独作为任务可调度性的证明。

#### 2.7.4 系统偶发卡死怎么保留现场？

建议记录：

- 当前任务和各任务状态。
- 每个任务的栈水位。
- 最近一次调度或心跳时间。
- 正在等待的队列、信号量或互斥锁。
- 中断嵌套、临界区和调度器挂起状态。
- HardFault 寄存器、PC、LR、SP 和复位原因。
- 最近若干条无阻塞事件日志。

调试阶段可以结合 FreeRTOS trace、运行时间统计、GPIO 翻转和 DWT 周期计数器测量实际执行时间与抖动。

### 第一等级：基础概念题

首先是基础概念

第一个高频问题

RTOS 中的任务有哪些状态

以 FreeRTOS 为例

比较常见的有运行态

就绪态

阻塞态和挂起态

其他三个就比较简单

挂起态则不一样

这个状态的使用是提高调度器性能的关键

任务调用 vTaskSuspend 以后

不会因为时间到了自动恢复

必须由其他任务或者中断显式唤醒

所以做周期任务的时候

不要用空循环一直查询系统时间

更不要为了等待外设

在高优先级任务里反复轮询

应该让任务进入挂起态

等事件真正发生以后再参与调度

这样 CPU 才能运行其他任务

或者在空闲时进入低功耗状态

第二个高频问题

就是高优先级任务一定会先运行吗

在抢占式调度下

如果一个更高优先级的任务进入就绪态

调度器会让它抢占当前的低优先级任务

但是高优先级不代表它始终都在运行

如果它正在等待队列

等待信号量

或者主动 Delay

那它处于阻塞态

CPU 仍然会交给低优先级的就绪任务

所以面试中如果被问到

任务优先级应该怎么设计

不能只回答数值越大越重要

还要结合任务的截止时间

执行周期和最坏执行时间

例如电机控制里的保护处理和控制任务

优先级通常高于通信和日志任务

但是高优先级任务每次执行也必须足够短

否则低优先级任务可能长期得不到运行机会

从而被饿死

### 第二等级：驱动应用与实时性题

进一步的，就是一些实际项目中的问题

最常见的就是

中断和任务之间应该怎么传递数据

比如 UART 收到一帧数据

或者 ADC DMA 完成一组采样

中断里不适合直接解析协议

也不适合做复杂的滤波和控制计算

更常见的方式是

中断先清除硬件标志

保存必要的数据

然后用队列

信号量或者任务通知

唤醒对应的处理任务

如果非要传递一份带内容的数据

也要最好使用队列并且使用非阻塞模式

但是这里一定要注意

为什么中断里不能直接使用普通接口

因为普通的队列和信号量接口

本来是给任务调用的

比如队列已经满了

普通的发送接口可以让当前任务进入阻塞态

等队列有空间以后再继续运行

但是中断不能阻塞等待

也不能按照任务的方式直接切换上下文

即使把等待时间配置成 0

普通接口内部的临界区和调度处理

仍然是按照任务上下文设计的

所以中断里要使用带 FromISR 后缀的接口

比如 xQueueSendFromISR

或者 vTaskNotifyGiveFromISR

这些接口不会在中断里阻塞

并且使用中断安全的临界区处理

另外 FreeRTOS 对能够调用系统 API 的中断优先级也有限制

优先级配置不符合要求

轻则触发断言

重则可能破坏内核数据结构

第二个问题

就是多个任务访问同一个外设应该怎么保护

比如一个高优先级控制任务

和一个低优先级诊断任务

都需要通过同一条 SPI 总线访问驱动芯片

这时候一般会用互斥锁

保证一次完整的 SPI 事务不会被另一个任务插进来

互斥锁和二值信号量看起来都只有可用和不可用两种状态

但互斥锁有所有者的概念

并且通常带有优先级继承机制

假设低优先级任务已经拿到互斥锁

这时候高优先级任务也来申请

它只能暂时阻塞

如果中等优先级任务又一直抢占低优先级任务

低优先级任务就迟迟没有机会释放锁

最后反而让高优先级任务等待得更久

这就是经典的优先级反转

启用优先级继承以后

持锁的低优先级任务会临时继承高优先级任务的优先级

尽快完成临界区并释放互斥锁

释放以后再恢复原来的优先级

但是优先级继承也不是所有实时性问题的保证

如果临界区本身特别长

持锁期间还去 Delay

或者等待另一个资源

高优先级任务依然可能被阻塞很久

所以工程上还要尽量缩短持锁时间

不要拿着锁做日志打印

也不要拿着锁等待外设的长时间超时

对于电流环这种硬实时控制

更不能把关键执行路径放在一个可能长期等待互斥锁的普通任务里

把任务状态

调度条件

中断通信

以及共享资源保护串在一起回答

面试官基本就能判断

你究竟只是调用过 RTOS 接口

还是认真处理过系统实时性问题
