# 串口通信 UART/USART 面试分享题库

> 适用场景：嵌入式软件、MCU 驱动开发、外设通信、工业现场通信、Bootloader/日志/模块通信方向面试分享。
>
> 说明：日常说的“串口”通常指 UART/USART 这类异步串行接口；TTL 串口、RS232、RS485 更多是电平/物理层概念。面试时要把“协议/控制器”和“物理电平/收发器”分开讲。

## 1. 分享主线

建议从一个常见问题切入：

```text
串口一帧数据是怎么传的？
    ↓
CPU 怎么接收串口数据：轮询 / 中断 / DMA？
    ↓
为什么一个字节一次中断会有瓶颈？
    ↓
DMA 为什么能降低 CPU 占用？
    ↓
DMA 遇到不定长数据怎么办？
    ↓
IDLE 中断 + DMA + 环形缓冲怎么设计？
    ↓
RS485 / Modbus / 高速连续流这些真实场景怎么处理？
```

这条线的优点是：先讲清楚 UART 基础，再自然进入工程设计，最后落到真实项目里的难点。

## 2. 第一层：基础知识

### 2.1 UART 是什么？为什么说它是异步通信？

UART 是 Universal Asynchronous Receiver/Transmitter，通用异步收发器。它把 CPU 要发送的并行数据转换为串行 bit 流，也把接收到的串行 bit 流恢复成字节。

“异步”的意思是通信双方没有共享时钟线。UART 只有 TX/RX 数据线，接收端根据双方约定好的波特率、起始位和采样规则来恢复数据。

面试回答：

> UART 是异步串行通信接口，发送端和接收端不共享时钟，而是提前约定波特率、数据位、校验位和停止位。接收端通过检测起始位开始同步，并在每个 bit 的中间位置采样。

工程注意点：

- 双方波特率必须接近，误差过大就会乱码。
- 双方数据格式必须一致，例如都配置为 `115200 8N1`。
- TX/RX 要交叉连接：A 的 TX 接 B 的 RX，A 的 RX 接 B 的 TX。
- 必须共地，否则接收端没有可靠的电平参考。

### 2.2 UART 和 USART 有什么区别？

UART 只支持异步串行通信。USART 是 Universal Synchronous/Asynchronous Receiver/Transmitter，既可以异步，也可以同步。

在很多 MCU 上，外设名字叫 USART，但实际项目大多数仍然按 UART 异步模式使用。

面试回答：

> UART 只支持异步模式，USART 多了同步模式，可以使用额外时钟线。但在常见 MCU 串口通信、日志、模块 AT 指令、RS485 等场景里，USART 通常也配置成异步 UART 使用。

### 2.3 UART 最少需要几根线？

最少需要：

- `TX`：发送。
- `RX`：接收。
- `GND`：公共参考地。

如果只单向发送，可以只接一根数据线加 GND。

常见连接：

```text
设备 A TX  -> 设备 B RX
设备 A RX  <- 设备 B TX
设备 A GND -> 设备 B GND
```

如果使用硬件流控，还会增加：

- `RTS`：Request To Send。
- `CTS`：Clear To Send。

### 2.4 `115200 8N1` 是什么意思？

`115200 8N1` 是最常见的串口参数写法：

| 字段 | 含义 |
| --- | --- |
| `115200` | 波特率，每秒传输 115200 个符号/bit，UART 场景常近似理解为 bit/s |
| `8` | 8 个数据位 |
| `N` | No parity，无校验位 |
| `1` | 1 个停止位 |

一帧 8N1 的实际 bit 结构：

```text
起始位  数据位0..7  停止位
  1        8          1
```

所以发送 1 个字节实际需要 10 bit 时间。

计算吞吐：

```text
115200 8N1
理论字节率 = 115200 / 10 = 11520 Byte/s
```

面试加分点：

> UART 波特率不等于有效 payload 字节率。8N1 每个字节有 1 个起始位和 1 个停止位，因此有效数据吞吐约为波特率的 80%。

### 2.5 UART 一帧由哪些部分组成？

典型 UART 帧：

```text
空闲高电平
起始位：低电平
数据位：通常 LSB first
可选校验位：奇校验/偶校验
停止位：高电平
空闲高电平
```

各部分作用：

- 起始位：告诉接收端一帧开始。
- 数据位：真正传输的数据。
- 校验位：做简单错误检测。
- 停止位：提供帧结束标志和一定时序容错。

### 2.6 接收端没有时钟线，怎么知道什么时候采样？

UART 接收端平时看到 RX 为空闲高电平。当 RX 从高变低时，认为检测到起始位。

接收端随后按本机波特率计时，通常在每个 bit 的中间位置采样。例如：

```text
检测到下降沿
等待半个 bit 时间，确认起始位仍为低
之后每隔 1 个 bit 时间采样一次
```

很多 UART 控制器会使用 8 倍或 16 倍过采样，提高抗抖动和抗误差能力。

面试回答：

> UART 通过起始位重新对齐接收时序。接收端检测 RX 下降沿后，在 bit 中间采样，后续按本地波特率继续采样数据位和停止位。双方时钟不能差太多，否则采样点会逐渐偏移到 bit 边沿甚至错位。

### 2.7 波特率误差为什么会导致乱码？

UART 每一帧只在起始位同步一次，之后数据位都靠本地时钟推算采样点。如果双方波特率误差过大，采样点会逐 bit 漂移。

例如 8N1 一帧有 10 bit。如果每 bit 都有一点误差，到最后一个数据位或停止位时，采样点可能已经偏到相邻 bit。

常见原因：

- MCU 时钟源不准。
- 晶振配置错误。
- APB/PCLK 配置错误，导致 UART 分频计算错。
- 双方波特率参数不一致。
- USB 转串口工具实际配置和程序不一致。

调试方法：

- 用逻辑分析仪解码 UART。
- 用示波器测单 bit 宽度。
- 检查 MCU 时钟树和 UART 外设时钟。
- 降低波特率验证是否改善。

### 2.8 奇偶校验能解决什么问题？

奇偶校验是在数据位后加 1 个 parity bit，用来让整帧中的 1 的个数满足奇数或偶数。

能检测：

- 单 bit 翻转。
- 奇数个 bit 翻转。

不能可靠检测：

- 偶数个 bit 翻转。
- 丢字节。
- 插入字节。
- 帧顺序错。
- 协议层字段错误。

面试回答：

> 奇偶校验是很弱的错误检测，只能发现部分 bit 错误。工程协议里如果数据重要，通常还要加 CRC、长度字段、序号、ACK/重传和超时机制。

### 2.9 FE、PE、NE、ORE 分别是什么？

常见 UART 错误：

| 错误 | 含义 | 常见原因 |
| --- | --- | --- |
| `FE` | Framing Error，帧错误 | 停止位采样不为高，波特率不匹配、噪声、格式错误 |
| `PE` | Parity Error，校验错误 | parity 配置不一致、数据受干扰 |
| `NE` | Noise Error，噪声错误 | 线路干扰、边沿质量差 |
| `ORE` | Overrun Error，溢出错误 | 新字节到来时旧数据还没被读走 |

重点是 ORE：

> ORE 往往说明软件处理不及时、ISR 卡住、DMA 没启动或优先级不合理。某些 MCU 上 ORE 不清除会导致后续接收异常，需要按芯片手册读 SR/DR 或调用 HAL 错误处理清标志并重新启动接收。

### 2.10 UART、TTL、RS232、RS485 是什么关系？

UART 是控制器/通信格式，定义如何按起始位、数据位、停止位发送字节。

TTL 串口、RS232、RS485 是不同电气层。

| 类型 | 特点 |
| --- | --- |
| TTL/CMOS UART | MCU 引脚电平，常见 3.3V/5V，板内短距离 |
| RS232 | 正负电压，点对点，常用于传统 PC/工业设备 |
| RS485 | 差分信号，抗干扰强，支持长距离和多节点，常用于工业现场 |

关键点：

```text
MCU UART 引脚不能直接接 RS232 总线
MCU UART 引脚也不能直接接 RS485 A/B 差分线
```

需要电平转换/收发器：

- TTL UART <-> RS232：MAX3232 类芯片。
- TTL UART <-> RS485：MAX485、SP3485、SN65HVD 系列等。

### 2.11 RTS/CTS 硬件流控是什么？

硬件流控用于避免接收方处理不过来导致丢数据。

常见理解：

- `RTS`：我是否准备好接收。
- `CTS`：对方是否允许我发送。

当接收方缓冲快满时，可以通过 RTS 告诉对方暂停发送。发送方看到 CTS 不允许后停止继续发。

面试回答：

> 硬件流控适合高速串口、大数据量、接收方处理能力不稳定的场景。它解决的是“对端来不及接收”的问题，不解决数据内容正确性，协议层仍可能需要 CRC 和重传。

## 3. 第二层：实践应用

### 3.1 UART 常见收发方式有哪些？

常见方式：

| 方式 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| 轮询 | 简单，容易理解 | CPU 阻塞，实时性差 | 初始化调试、低频少量数据 |
| 中断 | 不阻塞主流程，实时性较好 | 高频时中断负担大 | 中低速命令、AT 指令 |
| DMA | CPU 占用低，适合大数据 | 缓冲和边界处理复杂 | 高速流、不定长帧、大包传输 |

面试回答：

> 串口接收小数据可以用中断；连续高速数据或大包建议用 DMA。发送侧如果日志量大或不能阻塞，也适合使用 DMA + 发送队列。

### 3.2 阻塞式串口收发有什么问题？

阻塞发送：

```c
HAL_UART_Transmit(&huart1, buf, len, timeout);
```

可能问题：

- 调用期间 CPU 等待发送完成。
- 在 RTOS 任务中可能阻塞高优先级逻辑。
- 在中断中调用阻塞发送可能导致严重实时性问题。
- 多任务同时打印可能交叉。
- 波特率低时耗时明显。

例子：

```text
115200 8N1 发送 100 字节
耗时约 = 100 * 10 / 115200 = 8.68 ms
```

如果在控制环或高优先级任务里打印大量日志，会直接影响实时性。

### 3.3 中断接收一个字节一次有什么优缺点？

典型逻辑：

```text
启动接收 1 字节
    ↓
收到 1 字节进入 RX complete callback
    ↓
把字节放入 ring buffer
    ↓
重新启动接收 1 字节
```

优点：

- 简单。
- 适合 AT 指令、命令行、小流量协议。
- 不需要处理 DMA 指针。

缺点：

- 每个字节一次中断，高波特率下 CPU 压力大。
- 回调中处理太多逻辑会造成 ORE。
- 重新启动接收不及时可能丢字节。

估算：

```text
921600 8N1
有效字节率约 = 921600 / 10 = 92160 Byte/s
如果每字节一次中断，就是约 9.2 万次中断/秒
```

这个负担对很多 MCU 已经不合理。

### 3.4 为什么串口接收常用环形缓冲区？

UART 是字节流，数据到达时间和应用处理时间通常不同步。环形缓冲区用于解耦“接收”和“解析”。

结构：

```text
buffer[N]
write_index：接收侧写入位置
read_index ：解析侧读取位置
```

基本原则：

- 中断/DMA 负责尽快搬运字节，不做复杂解析。
- 主循环/任务从 ring buffer 取数据，做协议解析。
- 要处理满、空、回绕和溢出。

面试回答：

> 环形缓冲区可以把实时接收和慢速协议解析解耦。接收中断或 DMA 只负责写入 buffer，解析任务按自己的节奏读取，避免在中断里做复杂工作。

### 3.5 串口为什么会粘包/拆包？

严格说 UART 是字节流，没有“包”的概念。

应用层看到的粘包/拆包本质是：

- 一次接收回调可能包含半包。
- 一次接收回调可能包含多包。
- 两包之间没有天然边界。

解决方式是设计应用层帧格式。

常见分帧方式：

| 方式 | 例子 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 定长 | 每帧固定 16 字节 | 简单 | 灵活性差 |
| 分隔符 | `\r\n`、`0x7E` | 易读，适合文本 | payload 中出现分隔符要转义 |
| 长度字段 | 帧头 + 长度 + 数据 + CRC | 工程常用 | 解析稍复杂 |
| 超时分帧 | 一段时间没收到新字节认为结束 | 适合 Modbus RTU 类 | 依赖时间，受调度影响 |

### 3.6 推荐的二进制协议帧格式是什么？

一个常见结构：

```text
SOF       LEN       CMD       PAYLOAD       CRC
0xAA55    2B        1B        N bytes       2B/4B
```

字段作用：

- `SOF`：帧头，用于重新同步。
- `LEN`：payload 或整帧长度。
- `CMD`：命令字。
- `PAYLOAD`：数据。
- `CRC`：完整性校验。

解析策略：

1. 在字节流中寻找帧头。
2. 读长度字段，判断长度是否合法。
3. 等待整帧数据到齐。
4. 校验 CRC。
5. 分发命令。
6. 失败时丢弃部分数据并重新找帧头。

### 3.7 IDLE 中断是什么？为什么适合不定长接收？

UART IDLE line 表示接收线在接收完一个字符后，保持空闲状态超过一定时间。很多 MCU 会在检测到 IDLE 时产生中断。

它适合处理“不知道这次会收到多少字节”的场景：

```text
DMA 持续接收数据到 buffer
    ↓
一段时间没有新字节
    ↓
UART 触发 IDLE 中断
    ↓
软件根据 DMA 已接收长度取出这一段数据
```

面试回答：

> DMA 解决搬运数据的问题，但 DMA 本身不知道一帧什么时候结束。IDLE 中断可以在总线空闲时提示软件“这一段数据可能结束了”，所以 UART + DMA + IDLE 是处理不定长接收的常见组合。

注意：

- IDLE 是字符时间级别的空闲检测，不是协议层绝对帧结束。
- 如果两帧之间间隔很短，可能没有 IDLE。
- 如果协议本身有长度字段或结束符，应优先用协议解析确认边界。

### 3.8 DMA 普通模式和环形模式有什么区别？

DMA normal mode：

```text
启动 DMA 接收 N 字节
接满 N 字节或 IDLE 后停止/回调
软件处理数据
重新启动 DMA
```

适合：

- 一次一帧。
- 长度有限。
- 两帧之间有间隔。

风险：

- 重新启动 DMA 的空窗期可能丢数据。
- 连续高速流不适合频繁停止/启动。

DMA circular mode：

```text
DMA 一直向环形 buffer 写
写到末尾自动回到开头
软件根据 DMA 当前写位置取出新增数据
```

适合：

- 连续流。
- 高波特率。
- 不希望停止接收。

风险：

- 软件处理太慢会被 DMA 覆盖旧数据。
- 需要正确处理回绕。
- 需要设计溢出统计和丢弃策略。

### 3.9 DMA half-transfer、transfer-complete、IDLE 分别怎么用？

| 事件 | 含义 | 用法 |
| --- | --- | --- |
| HT | DMA 写到 buffer 一半 | 处理前半段数据 |
| TC | DMA 写到 buffer 末尾 | 处理后半段数据 |
| IDLE | UART 线空闲 | 处理当前未满的一段 |

环形 DMA 中常见处理：

```text
HT 事件：说明 0..N/2 有新数据
TC 事件：说明 N/2..N 有新数据
IDLE 事件：说明当前位置之前还有一段不满半包的数据
```

更通用的做法：

```text
每次事件发生
读取 DMA 当前写位置
计算 old_pos 到 new_pos 之间的新数据
把新数据交给协议解析
更新 old_pos
```

### 3.10 DMA + IDLE 的典型接收流程

普通模式：

```text
初始化 UART
启动 ReceiveToIdle DMA，buffer 大小 N
    ↓
收到数据，DMA 自动写 buffer
    ↓
发生 IDLE 或接满 N
    ↓
回调给出已接收 size
    ↓
复制/解析 buffer[0..size)
    ↓
重新启动 ReceiveToIdle DMA
```

环形模式：

```text
初始化 UART
启动 circular DMA
维护 old_pos
    ↓
HT/TC/IDLE 事件
    ↓
读取 DMA 剩余计数 NDTR
new_pos = buffer_size - NDTR
    ↓
处理 old_pos 到 new_pos 的新增数据
    ↓
old_pos = new_pos
```

面试回答：

> 对不定长串口，常用 UART RX DMA 搬运数据，再用 IDLE 中断判断一段数据结束。普通模式实现简单，但每次回调后要重新启动 DMA；连续高速流更适合 circular DMA，通过 DMA 写指针和软件读指针计算新增数据。

### 3.11 TX DMA 发送要注意什么？

发送侧也可以用 DMA，把内存中的数据搬到 UART TDR/DR。

注意点：

- DMA 传输完成只表示数据写入 UART 外设，不一定表示最后一个 bit 已经从 TX 引脚发完。
- 如果要控制 RS485 DE，通常要等 UART TC 标志，而不是只等 DMA TC。
- 发送 buffer 在 DMA 完成前不能被修改或释放。
- 多任务发送要加队列或互斥，避免数据交叉。

面试回答：

> TX DMA 适合大块数据或日志输出。DMA complete 不是总线发送完成，尤其 RS485 半双工切方向时必须等 UART TC，确认移位寄存器也发完了再拉低 DE。

### 3.12 RTOS 下串口驱动怎么设计？

推荐分层：

```text
ISR/DMA 回调层：只搬数据、置标志、发送事件
    ↓
驱动层：维护 ring buffer、错误恢复、发送队列
    ↓
协议层：解析帧、CRC、超时、命令分发
    ↓
业务层：处理业务逻辑
```

原则：

- 中断里不要做复杂协议解析。
- 中断里不要阻塞等待。
- 用 queue、stream buffer、event flag 通知任务。
- 发送使用单独队列，保证同一 UART 同一时间只有一个发送事务。
- 所有缓冲区溢出要有统计。

## 4. 第三层：具体场景拔高题

### 4.1 不定长数据如何用 UART + DMA + IDLE 可靠接收？

问题背景：

外部模块返回的数据长度不固定，例如 AT 指令响应、传感器上报、二进制协议帧。

推荐方案：

1. UART RX 使用 DMA。
2. 开启 IDLE 中断或使用 ReceiveToIdle 类接口。
3. 每次 IDLE/HT/TC 回调只取出新增字节。
4. 字节送入协议解析器。
5. 协议解析器根据帧头、长度、CRC 判断完整帧。

关键点：

- IDLE 只说明“线空闲了一段时间”，不等于协议帧一定完整。
- 真正的完整性要靠长度字段、结束符或 CRC。
- 如果连续两帧之间没有足够空闲，必须靠协议解析拆帧。

面试回答：

> 我会用 DMA 负责接收搬运，用 IDLE 事件减少不定长接收的回调频率，再把收到的字节放入 ring buffer 或协议解析器。IDLE 不是唯一帧边界，协议层仍要用帧头、长度和 CRC 判断完整帧。

### 4.2 高速连续串口流怎么设计？

场景：

921600、1Mbps、3Mbps 甚至更高波特率连续输入，CPU 无法逐字节中断处理。

设计：

- RX 使用 circular DMA。
- 使用较大的 DMA buffer，例如 1KB、4KB、8KB。
- 使用 HT/TC/IDLE 或定时轮询 DMA 写指针。
- 协议解析任务批量处理数据。
- 对处理不过来的情况定义策略：丢旧数据、丢新数据、限流、硬件流控。

需要估算：

```text
1 Mbps 8N1
有效字节率 = 1,000,000 / 10 = 100,000 Byte/s

如果 buffer = 4096 Byte
填满时间约 = 4096 / 100000 = 40.96 ms
```

这意味着软件必须在几十毫秒内搬走或处理这些数据，否则会覆盖。

### 4.3 DMA 环形缓冲如何处理回绕？

假设：

```text
buffer size = N
old_pos = 上次处理到的位置
new_pos = DMA 当前写入位置
```

如果：

```text
new_pos >= old_pos
```

新增数据是：

```text
buffer[old_pos .. new_pos)
```

如果：

```text
new_pos < old_pos
```

说明发生回绕，新增数据是两段：

```text
buffer[old_pos .. N)
buffer[0 .. new_pos)
```

伪代码：

```c
void uart_dma_process(void)
{
    uint16_t new_pos = BUF_SIZE - dma_get_remaining_count();

    if (new_pos == old_pos) {
        return;
    }

    if (new_pos > old_pos) {
        protocol_feed(&buf[old_pos], new_pos - old_pos);
    } else {
        protocol_feed(&buf[old_pos], BUF_SIZE - old_pos);
        if (new_pos > 0) {
            protocol_feed(&buf[0], new_pos);
        }
    }

    old_pos = new_pos;
}
```

面试关注点：

- 是否会漏掉回绕后的数据。
- 是否处理 `new_pos == old_pos`。
- 是否能检测处理太慢导致覆盖。
- 是否把 DMA 写指针和协议读指针概念分清楚。

### 4.4 `HAL_UARTEx_RxEventCallback` 里的 Size 怎么理解？

在 STM32 HAL 的 ReceiveToIdle 场景里，`Size` 常被误解。

通常要理解为：

> 到当前事件为止，DMA 接收缓冲区中已经写入到的位置或本次有效数据边界，而不是永远等于“新增长度”。

因此更稳妥的方式是维护上一次处理位置 `old_pos`，每次回调用 `Size` 或 DMA 当前指针算出 `[old_pos, new_pos)` 这一段新增数据。

注意：

- Normal DMA 下，`Size` 很像本次收到的长度。
- Circular DMA 下，更应该把它当当前位置。
- HT/TC/IDLE 都可能触发回调，不能假设只有 IDLE。

面试回答：

> 我不会直接把 Size 当作每次新增长度，而是维护 old_pos。每次回调拿到当前写位置后，计算 old_pos 到 new_pos 的差值，处理新增数据，并处理回绕。

### 4.5 为什么第一帧数据容易丢？

常见原因：

- UART/DMA 接收还没启动，外部模块已经发数据。
- 外部模块上电后自动上报，MCU 初始化顺序太晚。
- 使能 UART 前 RX 引脚状态不稳定。
- 清标志顺序不对，启动时已有错误标志。
- RS485 方向控制还在发送态，没有切到接收。
- 低功耗唤醒后 UART 时钟恢复太慢。

解决：

- 尽早初始化 UART RX。
- 外部模块加复位控制，等主机准备好再释放模块。
- 上电后丢弃第一段无效数据并等待协议帧头。
- 使用 ready/enable 引脚做握手。
- 启动接收前清错误标志。

### 4.6 ORE 溢出后怎么恢复？

ORE 表示 UART 接收数据寄存器还没被读取，下一个字节已经来了。

常见影响：

- 后续接收中断不再正常触发。
- HAL 状态机进入 error。
- DMA 接收停止。

恢复思路：

1. 读取并记录错误标志。
2. 按芯片手册清除 ORE。
3. 清空无效数据。
4. 重新启动 UART DMA/中断接收。
5. 统计一次 overrun，供现场诊断。

根因处理：

- 不要在中断里做耗时工作。
- 提高 UART/DMA 中断优先级。
- 使用 DMA 替代逐字节中断。
- 增大 ring buffer。
- 降低波特率或启用流控。

### 4.7 RS485 半双工如何控制 DE/RE？

RS485 常用半双工，两根差分线 A/B 上同一时刻通常只能一个节点发送。

收发器常见引脚：

- `DE`：Driver Enable，发送驱动使能。
- `/RE`：Receiver Enable，接收使能，通常低有效。

发送流程：

```text
拉高 DE，进入发送态
等待收发器使能稳定
UART 发送数据
等待 UART TC，确认最后一个 bit 发完
拉低 DE，切回接收态
```

为什么等 TC 而不是 TXE？

- `TXE` 表示发送数据寄存器空，可以写下一个字节。
- `TC` 表示移位寄存器也空，最后一个 stop bit 已经发完。

如果 TXE 后就拉低 DE，最后几个 bit 可能还没真正上总线，会被截断。

面试回答：

> RS485 半双工切方向必须等 UART TC。DMA 完成或 TXE 只说明数据进入外设，不代表线上的最后一位已经发完。

### 4.8 RS485 多节点如何避免冲突？

RS485 电气层允许多节点挂在同一总线上，但不自动解决谁能发送。

常见策略：

- 主从轮询：只有主机点名的从机能回复。
- 令牌机制：拿到令牌的节点才能发。
- 应用层仲裁：发送前监听，冲突后随机退避。
- 固定时隙：每个节点在自己的时间窗口发送。

工业现场最常见的是主从轮询，例如 Modbus RTU。

硬件注意：

- 总线两端加终端电阻。
- 总线空闲需要偏置，避免悬空误触发。
- 分支线不要太长。
- A/B 极性接反会通信失败。

### 4.9 Modbus RTU 为什么用 3.5 字符时间判断帧间隔？

Modbus RTU 是典型基于 UART/RS485 的协议。它没有固定帧头，而是用时间间隔区分帧。

规则概念：

- 帧内字符之间间隔不能太长。
- 帧与帧之间需要至少 3.5 个字符时间的空闲。

字符时间估算：

```text
Tchar = 每字符 bit 数 / 波特率

例如 9600 8N1：
Tchar = 10 / 9600 = 1.0417 ms
3.5T = 3.65 ms
```

和 IDLE 的关系：

- UART IDLE 通常约 1 个字符时间空闲就触发。
- Modbus RTU 帧结束要求约 3.5 个字符时间。
- 所以 IDLE 可以作为“有空闲”的提示，但严格 Modbus 仍应按协议要求计时。

### 4.10 日志串口影响实时任务怎么办？

问题：

大量 `printf` 走串口会阻塞 CPU，影响实时控制和通信。

方案：

- 日志写入内存 ring buffer，后台低优先级任务发送。
- UART TX 使用 DMA。
- 日志分级，现场默认关闭 DEBUG/TRACE。
- buffer 满时允许丢日志，而不是阻塞关键任务。
- 对关键日志做压缩或二进制格式。
- 提供运行时开关。

面试回答：

> 日志不能阻塞实时路径。实时任务只把日志写入内存队列，低优先级任务用 DMA 慢慢发。队列满时根据策略丢弃低优先级日志，并统计丢弃次数。

### 4.11 多任务同时发送 UART 如何避免数据交叉？

错误做法：

```text
任务 A 正在发送 "ABC"
任务 B 同时发送 "123"
实际输出可能变成 "A1B2C3"
```

解决：

- 给 UART 发送加 mutex，保证一次发送原子。
- 更推荐：所有任务把消息投递到 UART TX queue，由单独发送任务串行发送。
- DMA 发送完成后再启动下一包。

推荐结构：

```text
任务 A/B/C
  ↓
UART TX Queue
  ↓
UART TX Worker
  ↓
DMA transmit
  ↓
TX complete callback 通知发送下一包
```

### 4.12 低功耗下 UART 唤醒会不会丢第一字节？

可能会。

原因：

- MCU 从低功耗恢复需要时间。
- UART 时钟恢复需要时间。
- 起始位到来时外设可能还没完全准备好。

解决：

- 使用支持 UART wakeup 的低功耗模式和外设。
- 降低唤醒串口波特率。
- 协议前增加唤醒前导字节。
- 发送端先发 dummy/preamble，再发正式帧。
- 用外部 GPIO/IRQ 先唤醒，再开始 UART 发送。

### 4.13 UART Bootloader/升级协议怎么设计？

关键点：

- 帧头、命令、地址、长度、数据、CRC。
- 分包传输，避免单包过大。
- ACK/NACK。
- 超时重传。
- 写 Flash 前校验地址范围。
- 整包升级完成后做固件整体 CRC/hash。
- 断电保护：双分区或回滚机制。
- 防止非法跳转：校验栈顶和 reset handler 地址。

典型帧：

```text
SOF | CMD | ADDR | LEN | DATA | CRC
```

面试回答：

> UART Bootloader 重点不是能收数据，而是可靠性和异常恢复。要有分包、CRC、ACK/重传、超时、Flash 地址校验、整包校验和断电保护。

### 4.14 串口偶发无响应如何定位？

按层次查：

1. 物理连接：TX/RX 是否交叉、GND 是否共地、电平是否匹配。
2. 波形：波特率是否正确、是否有噪声、边沿是否畸变。
3. UART 错误标志：FE、PE、NE、ORE。
4. DMA 状态：是否仍在运行、NDTR 是否变化。
5. 中断状态：IDLE/RXNE/TC 是否触发，优先级是否被屏蔽。
6. 缓冲区：ring buffer 是否满，是否覆盖。
7. 协议状态机：是否卡在等待长度/CRC/结束符。
8. 任务调度：协议任务是否被高优先级任务饿死。
9. 对端状态：对端是否复位、忙、流控暂停或方向没切回。

面试回答：

> 我会先确认物理层和波特率，再看 UART 错误标志和 DMA 是否还在搬数据，最后看缓冲区和协议状态机。定位串口问题不能只盯业务层，很多偶发问题根因是 ORE、方向控制或波形质量。

## 5. 典型面试题与回答模板

### 5.1 轮询、中断、DMA 怎么选？

回答模板：

> 数据量小、初始化阶段可以用轮询；中低速命令交互可以用中断接收；高速连续数据或大包传输应该用 DMA。DMA 不是自动解决所有问题，它只解决数据搬运，帧边界、缓冲区溢出、错误恢复和协议解析仍要软件设计。

### 5.2 为什么 DMA 接收还需要 IDLE 中断？

回答模板：

> DMA 只知道把 UART 收到的字节搬到内存，不知道应用层一帧什么时候结束。如果接收长度不固定，就需要 IDLE、超时、结束符或长度字段来判断边界。IDLE 是常见硬件辅助方式，能在串口空闲时通知软件处理当前已收到的数据。

### 5.3 如何设计一个可靠的串口协议？

回答模板：

> 我会使用帧头、长度、命令、payload、CRC 的结构。解析时先找帧头，再检查长度合法性，等整帧到齐后校验 CRC，通过后分发命令。异常数据要能丢弃并重新同步，不能让状态机卡死。需要可靠传输时再加序号、ACK/NACK、超时重传。

### 5.4 串口乱码的常见原因有哪些？

回答模板：

> 首先查波特率和数据格式是否一致，例如 8N1、校验位、停止位。其次查 MCU 时钟配置和 UART 分频。再查电平是否匹配、是否共地、TX/RX 是否接反。最后用逻辑分析仪看实际 bit 宽度、帧错误和噪声。

### 5.5 UART DMA 接收为什么还会丢数据？

回答模板：

> DMA 只能减少 CPU 搬运压力，但如果 buffer 太小、处理任务太慢、DMA 被停止重启期间有空窗、cache 没处理、ORE 错误没恢复，仍然会丢数据。连续高速流更适合 circular DMA，并且要有溢出检测和限流策略。

### 5.6 RS485 为什么需要方向控制？

回答模板：

> RS485 半双工总线上同一时刻通常只能一个节点发送。MCU 通过 DE/RE 控制收发器进入发送或接收状态。发送完成后必须等 UART TC 再关闭 DE，否则最后一个字节可能还没完全发到总线上。

### 第一等级：基础概念题

首先是基础知识

一般是简历里面重点写了用了一些高级串口功能才会涉及

例如什么是

数据位

校验位

停止位

我们的接收端通过起始位

重新对齐接收时序

后面再按照本地波特率去采样

这就叫异步

第二个常见的基础问题就是

一般我们使用115200波特率的串口

数据传输的速率可不是115200bit/s

因为还要加上起始位和终止位，

所以每10个bit才真正传输一个字节

### 第二等级：驱动应用题

这些都是最基础的问题了，其实出现概率很低，

主播遇到的更多是下面这种和项目强耦合的问题

比方请你回答一下串口一共有哪些收发方式

最简单的是轮询

轮询好理解

但是会阻塞 CPU

所以一般适合初始化调试

或者特别低频的数据

然后是中断接收

中断接收适合命令交互

比如 AT 指令

或者一些中低速小数据量场景

但是一个字节进一次中断

如果是 921600 的波特率

那就是每秒 9 万多次中断

这基本上会让其他任务抢不到时间片

所以高速数据

大包数据

或者连续数据流

一般就会考虑 DMA

但是这里一定要注意

DMA 不是万能的

DMA 只解决一件事

就是把 UART 收到的数据

自动搬到内存里面

它并不知道你一帧数据什么时候结束

而串口本质上是字节流

没有天然的包边界

所以这时候就会引出一个很经典的问题

为什么 DMA 接收还需要 IDLE 中断？

因为 DMA 负责搬运数据

IDLE 负责告诉软件

串口线已经空闲了一段时间

这一段数据可以拿出来处理了

所以不定长接收里面

常见方案就是 UART + DMA + IDLE

DMA 负责搬运

IDLE 负责触发处理

协议层再用帧头

长度

CRC

去判断这一帧到底完不完整

这里大家一定要注意

IDLE 不等于一帧结束

它只是说明线路空闲了一段时间

如果两帧间隔很短

或者协议本身是连续流

最终还是要靠协议层去拆包

如果能完整回答这些，

起码能让面试官觉得你是写过相关驱动的

### 第三等级：项目实战题

进一步的，就是看你是否真的踩过串口相关的坑

例如

不定长数据怎么用 DMA + IDLE 可靠接收？

比较完整的回答是

UART RX 开 DMA

然后开启 IDLE 中断

收到数据之后

DMA 自动把数据写到 buffer 里面

一旦发生 IDLE

或者 DMA 半满

或者 DMA 满

软件就读取当前 DMA 写到了哪里

只处理这一段新增数据

然后把数据丢给 ring buffer

或者直接丢给协议解析器

协议解析器再根据帧头

长度

CRC

判断完整帧

第二个问题

Circular DMA 怎么处理回绕？

这个问题非常容易看出项目经验

因为 circular DMA 会一直往一个ring buffer 里写

写到末尾之后

自动回到开头

所以软件要维护一个 old_pos

也就是上次处理到哪里

然后每次事件进来

再读取当前 DMA 的 new_pos

如果 new_pos 大于 old_pos

那新增数据就是 old_pos 到 new_pos 之间这一段

反之说明已经回绕了

那就先处理 old_pos 到 buffer 末尾

再处理 buffer 开头到 new_pos

这个逻辑说清楚

面试官基本就知道你是真写过

不是只会调用一个 HAL_UARTEx_ReceiveToIdle_DMA

第三个问题

就是 ORE 溢出怎么处理

ORE 的意思是

旧数据还没被读走

新数据又来了

常见原因就是中断里做了太多事情

DMA 没有及时启动

buffer 太小

或者任务调度不及时

这时候就需要从根本原因上优化

比如减少中断耗时

提高 UART 或 DMA 中断优先级

增大 ring buffer

或者降低波特率
